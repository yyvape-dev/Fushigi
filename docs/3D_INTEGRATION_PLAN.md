# 3D統合計画（地形・光は3D、キャラ・演出は既存の2D）

作成：2026-10-24。事実と仮説は分けて書く。参照実装：`experiment3d.html`（本編マージ済み・本編からは未使用）。

## 0. 結論と判断（事実）
- ユーザーが実機で確認：「65°がかなり本家感ある」。キャラが太って見えた原因は、板（ビルボード）の縦つぶれ。足元基準で傾けて補正済み（`LEANS`、標準=大）。
- 壁の北側で主人公が隠れる問題は「不要」（ユーザー判断）。この計画では扱わない。
- 現状の描画は2D Canvas（`index.html` の `function draw()`、2700行付近。地形タイル→罠→アイテム→敵→霧→主人公→手前の敵→演出の順に描く）。

## 1. 方針（提案＝仮説）
**案A（推奨・低コスト）：WebGLキャンバスを `#c` の背面に置き、地形と光だけ3D。キャラ・アイテム・演出は既存の2D描画を、3Dの投影座標に合わせて重ねる。**
- 理由：敵・仲間・店・演出（`drawEntity` `AllySystem.draw` `EventVfx` など約10系統）を書き換えずに済む。読むコードが少ない＝トークンが少ない。
- 弱点：キャラが壁に隠れない（ユーザーが不要と判断済み）。3D空間の本物の影はキャラに落ちない（丸影は2Dで足せる）。
- 案B（後で検討）：全キャラを3Dの板にする。深度・影は正しくなるが、全系統の書き換えが要る。案Aで満足なら不要。

## 2. 構成
- 新規 `assets/render3d.js`（`window.Render3D`）。three.js は `assets/vendor/three.module.min.js`（ESM）。本編が classic script 構成のため、`render3d.js` は ESM で読み込み、完了後に `window.Render3D` を公開する。
- 設定「3D表示」（既定OFF）。OFFまたはWebGL不可なら従来の2D描画のまま（フォールバック）。町（`scene==='town'`）は常に2D。
- `Render3D` の公開関数（案）：
  - `init(canvasParent)`：WebGLキャンバスを `#c` の背面に作る。失敗時は `false`。
  - `setLevel({map, W, H, themeId, stairs})`：階の生成時に呼ぶ。壁・床・階段の3D地形を作る。
  - `frame({vx, vy, tPlayer, tiltDeg, lean})`：毎フレーム。カメラを主人公の表示座標に追従して描画。
  - `project(x, y)`：マス座標 → 画面座標 `{px, py, scale}`。2Dの敵・主人公描画の位置合わせに使う。
  - `active()`：3Dが使われているか。
- `index.html` の変更箇所（最小）：①階の生成直後に `setLevel` ②`draw()` で3D時は地形タイル・陰影・霧・ぼかし（`blit(key…)`のループ、`shadeTile`、`DungeonExperience.fog`、`depthBlur`）を飛ばし、背景を透明にクリア ③敵・主人公・アイテムの `camX/camY` を `project` で置換 ④設定UIに「3D表示」。
- 描画しない（据え置き）：HUD、ミニマップ、メッセージ窓、操作盤、演出（斬撃・数字）。HTML/2Dのまま上に重ねる。

## 3. 段階（各段階は別の会話で完結。合格基準を満たしてから次へ）
**段階1：地形＋主人公（3D表示ON時のみ）**
- 内容：`render3d.js` 新規、`setLevel`/`frame`/`project`、`draw()` の3分岐、設定「3D表示」。主人公は `drawEntity('player',…)` を `project` の座標に重ねて描く。カメラ標準65°、キャラは縦補正（2Dでは `ctx.scale(1, k)` で縦つぶれを戻す）。
- 合格基準：`node tests/harness.js index.html tests/test_mvp.js` が `ALL OK`（3D OFFで従来どおり）／実機で1階を歩いて、本編の移動・攻撃・階段が2Dと同じに動く／3D ONでも敵が正しいマスに見える（段階2前でも位置ずれが目立たない）。
- 未確認（仮説）：2D描画のスケール（`TS`）と3Dのカメラ距離を一致させる式。実機で合わせる。

**段階2：敵・仲間・店・アイテム・罠の位置合わせ**
- `project` で全 `drawEnt` と床アイテム、罠、足元表示を置換。演出（`EventVfx`/`drawVfx`/`EnemyVfx`）の座標も `project` 経由に。
- 合格基準：全敵種（60種）と店・仲間・罠で、足元が地面のマスに合って見える。

**段階3：光と雰囲気**
- 部屋ごとの照明（現行 `DungeonExperience.fog` の部屋点灯の代替）、階段の光、ロケーション別の色味（霧・環境光）、松明の揺れ。
- 合格基準：2D版の「暗さ・明るさ」と比べて、劣化しない（ユーザー判断）。

**段階4（任意）：案Bへの拡張**：案Aで不満が出たときのみ。

## 4. 作り方のルール（トークン節約）
- `assets/vendor/*` は読まない。`index.html` は全文を読まず、`grep -n` と offset/limit で必要範囲だけ。
- 3D関連のコードは `render3d.js` に集める。`index.html` に足すのは呼び出しだけ。
- 画面確認は Playwright（`--use-gl=swiftshader`）で。headlessのfpsは実機の目安にならない。テスト用ハーネス（`@napi-rs/canvas`）にはWebGLが無いため、`Render3D` は未対応環境で何もしない（`active()===false`）こと。
- 絵は新規に作らない（既存の `assets/dungeon/locations-v1/`・8方向コマ絵を流用）。

## 5. リスク（仮説）
- スマホ実機の性能：影（点光源の影）が重い可能性。設定で影のON/OFFを持たせる。
- 2Dの `TS`（1マスのpx）と3D投影の不一致で、キャラのサイズが段階ごとに変わる。段階1で式を決めて固定する。
- `index.html` の `draw()` は演出が絡み合っているため、分岐を足す際に既存の描画順を壊さないこと（テストは画面を見ないため、実機確認が必要）。
